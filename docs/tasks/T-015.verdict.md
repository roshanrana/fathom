- AC2 (malformed 2xx body → PROVIDER_HTTP "malformed response", body never leaks): **FAIL**.
  Confirmed correct handling for `{"choices": []}`, `{"foo": 1}`, `"not json"` (invalid JSON),
  `{"choices": [{"message": {}}]}`, top-level `[]`, top-level `null` (and the Anthropic
  analogues `{"content": []}`, `{"content": [{}]}`) — all raise `FathomError(PROVIDER_HTTP,
  reason="malformed response")` with no body leakage. However, the case explicitly listed in
  the verification procedure — `{"choices": [{"message": {"content": null}}]}` (Portkey) and its
  Anthropic analogue `{"content": [{"type": "text", "text": null}]}` — raises an **uncaught
  `pydantic.ValidationError`**, not `FathomError`. Reproduction:
  ```
  handler returns 200 {"choices": [{"message": {"content": null}}]}
  provider.complete_json(...) raises:
    pydantic_core._pydantic_core.ValidationError: 1 validation error for ProviderResult
    text: Input should be a valid string [type=string_type, input_value=None, ...]
  ```
  Root cause: `_parse_portkey_payload`/`_parse_anthropic_payload` only catch
  `(json.JSONDecodeError, KeyError, IndexError, TypeError)` around the dict/index lookups. When
  the key exists but its value is `None`, no lookup exception is raised — `text` is bound to
  `None` and returned successfully from the parse helper. The `ValidationError` is raised later,
  in `ProviderResult(text=text, ...)` construction, outside any `try`/`except` in
  `complete_json`, so it escapes the provider as a raw (non-`FathomError`) exception. This is a
  D-010 violation ("No raw ... exception[s] escape[s] a provider") and a gap against the pack's
  own AC2 wording ("each raise `PROVIDER_HTTP` with reason `malformed response`"). It is also
  not covered by any test in `tests/test_providers.py` — the implementer's malformed-body
  parametrizations omit the null-content shape entirely, even though it is the shape most likely
  to occur in practice (a real 2xx response with an empty/refusal completion).

## Findings

**CRITICAL** — `fathom/providers.py`: `_parse_portkey_payload` (used by `PortkeyProvider`) and
`_parse_anthropic_payload` (used by `AnthropicProvider`) do not guard against a present-but-`None`
completion-text value. A 2xx body such as `{"choices": [{"message": {"content": null}}]}`
(Portkey) or `{"content": [{"type": "text", "text": null}]}` (Anthropic) passes the
`try`/`except (json.JSONDecodeError, KeyError, IndexError, TypeError)` block unharmed (`text =
None` is a valid assignment, no exception raised at that point), and the resulting
`pydantic.ValidationError` from `ProviderResult(text=None, ...)` is raised outside any
`FathomError`-producing guard, propagating as a raw exception out of `complete_json`. This is
exactly the class of case D-010 and the pack's AC2 are meant to close, and it is the case most
plausible in production (a gateway returning HTTP 200 with an empty/null completion, e.g. a
content-filtered or truncated response). Fix: validate that the extracted `text` is a non-`None`
`str` inside the existing `try` block (e.g. add an explicit check that raises via the same
malformed-response path, or include the emptiness check before constructing `ProviderResult`) for
both parse helpers.

No other findings. All other tested transport-error and malformed-body shapes, the CLI exit-2
path, and the CLI `(no source)`/JSON-unchanged rendering behave exactly per spec and the pack's
message forms.
