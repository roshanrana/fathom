# Security review T-019 — FINDINGS
Boundary: B6  Risk class: medium

1. [HIGH] `PriceClient._bars_from_yahoo` (fathom/live/prices.py) runs entirely outside the
   `try/except (json.JSONDecodeError, KeyError, IndexError, TypeError)` block in `_yahoo()` —
   that block only wraps `json.loads(body)` + `payload["chart"]["result"][0]`. A null entry in
   Yahoo's `timestamp` array raises an uncaught `TypeError` from
   `datetime.fromtimestamp(None, tz=UTC)`, and a non-numeric string in `open`/`high`/`low`/
   `close`/`volume` raises an uncaught `ValueError` from `float(...)` (`_safe_float` and the
   direct `float(cast(float, close))` call). Both cases are real, documented Yahoo response
   shapes (pre/post-market gaps, maintenance pages served as 200s) and both bypass the
   documented Yahoo→Stooq fallback entirely instead of surfacing as `SOURCE_HTTP` — control
   C-09 — fix required before merge.

2. [HIGH] `PriceClient._stooq` (fathom/live/prices.py) enforces no row cap on
   `pd.read_csv(io.StringIO(text))` (design/task expects ≤ 10,000 rows) and does not reject
   non-numeric cells safely: `row["Open"]/["High"]/["Low"]/["Volume"]` go straight into
   `float(...)` and `row["Date"]` into `datetime.strptime(...)` with no try/except, so a
   malformed or oversized Stooq CSV (up to the 25 MB `LiveHttp` cap, i.e. hundreds of thousands
   of rows) raises an uncaught `ValueError` instead of a clean `SOURCE_HTTP`/`SOURCE_EMPTY` —
   control C-09 — fix required before merge.

3. [MEDIUM] Neither `PriceClient.daily_bars` (ticker) nor `facts.snapshot` (cik) validates its
   identifier against a safe pattern (e.g. `^[A-Z0-9.\-]{1,10}$`) before interpolating it into
   the Yahoo/Stooq/SEC URL templates; both rely entirely on an as-yet-unwritten caller (no
   `live/build.py` exists yet in this diff) to have validated the value upstream — control
   C-09 — fix required before merge.

4. [MEDIUM] `facts.snapshot`/`_numeric_val` (fathom/live/facts.py) never checks
   `math.isfinite()` on `shares`/`eps_ttm`/`equity`/`dps_ttm`. Python's `json.loads` accepts the
   non-standard `NaN`/`Infinity`/`-Infinity` tokens by default, so a corrupted or malicious
   `companyconcept` response can flow straight through `_numeric_val` (which only rejects
   `bool`/non-numeric types) into `market_cap`/`pb`/`dividend_yield`; the `equity != 0` and
   `last_close != 0` guards do not catch a NaN operand (`NaN != 0` is `True` in Python), so a
   non-finite value can be returned instead of `None` and later break strict JSON serialisation
   — control C-09 — fix required before merge.

5. [LOW] No sanity bound on fact magnitude (shares, eps_ttm, equity, dps_ttm) before arithmetic
   in `facts.snapshot` — an absurdly scaled XBRL value (e.g. a units/scale mismatch) is silently
   accepted into `market_cap`/`pe`/`pb` rather than rejected — control C-09 — accepted
   candidate.
