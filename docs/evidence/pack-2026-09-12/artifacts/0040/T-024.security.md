New finding (this attempt, a sibling defect on the same code paths this task hardened, not

1. [HIGH] `SecClient.ticker_map` (sec.py:211, `entry["ticker"]`), `SecClient.lookup` (sec.py:227,
   `entry["cik_str"]`), and `SecClient._to_filing` (sec.py:321-323, `entry["form"]`/
   `entry["accessionNumber"]`/`entry["primaryDocument"]`) index directly into per-entry `dict`
   values pulled out of the payload `_decode_json` returns. `_decode_json` only guarantees the
   *top-level* body parsed as JSON and is a `dict` — it says nothing about the shape of the
   per-ticker or per-filing entries nested inside. A response whose bytes are corrupted just
   enough to alter a key name or a string value, but not enough to break JSON syntax (a
   realistic outcome of a 1-8 byte mutation on a large SEC body — a flaky connection, a caching
   proxy, or an adversarial position between the client and `data.sec.gov`), leaves a
   structurally valid JSON object with an entry missing `"ticker"`/`"cik_str"`/`"form"`/etc., and
   the direct `entry[...]` index then raises a bare `KeyError` — not `FathomError` — exactly the
   uncaught-exception failure mode this task was supposed to eliminate, just one level deeper
   (per-entry field access, not whole-body decode). `fathom/live/build.py:154-155`
   (`company = sec.lookup(symbol)` / `filings = sec.filings(company.cik)`) has no surrounding
   try/except, so this reaches the `materialize()` pipeline entry point uncaught, same blast
   radius as the T-023 attempt-4 HIGH just closed above. Evidence: the task's own AC2 test,
   `test_fr021_fuzz_mutated_submissions_and_ticker_map_raise_only_fathom_error` (seed 20240024,
   200 iterations), fails deterministically on this exact `KeyError: 'cik_str'` at
   `sec.py:227`. Independently reproduced with a different seed (999024, 1000 iterations, this
   review's own `MockTransport` harness): `lookup()` 1/1000 uncaught `KeyError: 'ticker'`,
   `filings()` 1/1000 uncaught `KeyError: 'primaryDocument'` — low rate because most random
   1-8-byte mutations of a multi-KB/MB JSON body do break JSON syntax outright (caught cleanly
   by `_decode_json`), but non-zero and reproducible, and the task's own deterministic seed is
   proof it isn't a fluke. `company_concept`/`facts.snapshot` (0/1000 uncaught in the same fuzz
   run) and `document_text`/`daily_bars` (both sources, 0/1000) are not affected — `snapshot`
   already treats malformed per-fact shapes as skippable-not-raising by frozen design (facts.py
   docstring), and `document_text` decodes with `errors="replace"` into tolerant HTML parsing.
   Neither the `KeyError`'s own text nor anything else observed contains response-body or URL
   content (a bare Python key-name string only) — control C-09 (availability/contract), not
   C-12 — but it is squarely an uncaught exception reachable from untrusted network data,
   meeting this round's HIGH bar. Fix: validate presence/type of the fields each caller reads
   off a decoded entry before indexing (e.g. `entry.get("ticker")` / `.get("cik_str")` with a
   `FathomError` raise mirroring `_invalid_edgar_field_error`, already used elsewhere in this
   file for other untrusted EDGAR fields), rather than raw `entry[...]` indexing, for every field
   read from a `_decode_json`-derived entry in `ticker_map`, `lookup`, and `_to_filing`.

New finding (this attempt, a sibling defect on a code path adjacent to what this task hardened,
not touched by this diff, not caught by the task's own AC2 fuzz test because it needs a
*structural* field-shape change rather than a random 1-8-byte mutation of a large real fixture):

1. [HIGH] `SecClient.lookup` (sec.py:294-295):
   ```python
   exchanges = cast(list[object], submissions.get("exchanges") or [])
   exchange = str(exchanges[0]) if exchanges and exchanges[0] else None
   ```
   `submissions` is the raw `dict` returned by `_submissions()` — `_decode_json` only guarantees
   the *top level* parsed as a JSON object, exactly as documented in `_decode_json`'s own
   docstring (sec.py:132-135) as the class of gap this task exists to close for nested fields.
   `cast(list[object], ...)` is a `typing`-only annotation with zero runtime effect; it does not
   verify `submissions["exchanges"]` is actually a list. A response where `exchanges` is any
   other truthy, non-empty-list JSON value — a `dict` (`{"a": 1}`) or a bare number (`5`) both
   confirmed by this review — makes `exchanges[0]` raise a bare `KeyError` or `TypeError`, not
   `FathomError`, exactly the uncaught-exception failure mode this task exists to eliminate, one
   field over from the ones already fixed. Evidence (this review's own `MockTransport` harness,
   not in the existing suite): `sec.lookup("AAPL")` with `submissions["exchanges"] = {"a": 1}`
   raises uncaught `KeyError: 0`; with `submissions["exchanges"] = 5` raises uncaught
   `TypeError: 'int' object is not subscriptable`. Confirmed end-to-end through the public
   pipeline entry point: `live_build.materialize("AAPL", settings, force=True, http=http)` with
   the same corrupted submissions body raises the same bare `KeyError: 0` — `materialize`'s
   `company = sec.lookup(symbol)` (`fathom/live/build.py`, no surrounding try/except) is
   unprotected, same blast radius as the closed attempt-1 HIGH. No partial
   `<live_cache_dir>/AAPL/` directory is left (`live_dir.mkdir` at `build.py:188` runs strictly
   after the `lookup()`/`filings()` calls that would raise first), so there is no accompanying
   LOW here for cache-directory hygiene. Neither exception's own text contains response-body or
   URL content (a bare key name / type name) — control C-09 (availability/contract), not C-12 —
   but it squarely meets this round's HIGH bar: an uncaught exception reachable from untrusted
   network data. A 2000-iteration random-byte mutation re-fuzz of the same two call sites (seed
   999024) found 0/2000 uncaught, confirming this is a genuine gap in the *type* of fuzzing
   done, not something the existing seeded test would ever have caught by chance — a real
   adversary or a misbehaving/compromised proxy between the client and `data.sec.gov` controls
   the full response shape, not just individual bytes of an otherwise-valid fixture. Fix:
   validate `submissions.get("exchanges")` is a `list` (and, if non-empty, that `exchanges[0]`
   is a `str` or falls back to `None`) before indexing — mirror the guard style already used for
   `ticker_map`/`_valid_table_rows` rather than a bare `cast`.
   `submissions.get("sicDescription")`/`submissions.get("fiscalYearEnd")`/
   `submissions.get("name", ...)` (sec.py:296-301) were checked for the same class of bug and
   are safe: all three are passed through `str(...)` (which coerces any type without raising)
   rather than indexed.
